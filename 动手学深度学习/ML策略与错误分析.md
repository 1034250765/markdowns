## 机器学习开发的迭代循环（P79）

前面的课程都在回答"怎么训练出一个模型"，但真实项目里更多时间花在"怎么让模型变好"。这一集给出贯穿整个项目的工作框架。

### 循环四步

```
   1. 选架构 ───► 2. 训练模型 ───► 3. 诊断 + 错误分析
  (选模型、选数据、  (拟合参数、      (验证集上错在哪、
   定第一版架构)      调超参数)        还缺什么)
      ▲                                            │
      │                                            ▼
      └──────── 4. 把精力投到最有价值的改进 ◄────────┘
                (加数据？换模型？改特征？→ 回到 1)
```

| 步骤 | 做什么 | 关键点 |
|------|--------|--------|
| 1. 选架构（architecture） | 定下第一版系统架构 | 选什么模型、用什么数据——收集/整理数据也算在这步 |
| 2. 训练模型 | 得到第一版能跑的模型 | 拟合参数、跑通流程，先不求完美 |
| 3. 诊断与错误分析 | 看清模型差在哪 | 学习曲线（P73）、错误分析（P80） |
| 4. 改进决策 | 把精力投到最值的地方 | 加数据 / 换架构 / 加特征……然后回到 1 |

两点强调：

- **这是循环（iterative loop），不是直线**：第一版模型不是终点而是起点，之后绝大部分时间都在"训练—诊断—改进"里转圈。
- 第 4 步的选项远不止"加数据"一种——诊断结果告诉你该选哪条，这正是 P81、P82 要展开的内容。

经验就积累在这个循环里：转的轮数多了，判断"下一步投什么"会越来越准。（对应我们：benchmark 定下"5 个模型 × 4 个测试集"，正对应第 1 步"选架构"——先想清楚选什么模型、用什么数据，第一版跑通后，后面每轮改动才有可比的基准。）

一句话：**模型开发的产出不止是模型，还有"下一轮该做什么"的判断。**

## 错误分析（P80）

错误分析（Error Analysis）是循环第 3 步的核心手法：**在验证集上取出被错分的样本，人工逐个查看，按错误类型分桶（bucket）统计占比，用占比决定"值不值得为这类错误投入"。**

> 也就是说：错误分析反复看的是验证集，测试集只留给最终评估。

### 经典例子：垃圾邮件分类器

垃圾邮件系统在验证集 500 封里错分了 100 封。这 100 封错例里，哪一类最值得先投入？做法：人工逐封查看、按错误类型分桶（列课件给出的主要几桶）：

| 错误类型 | 数量（/100） | 推论 |
|---------|-------------|------|
| 药品广告（pharma） | 21 | 最大桶 → 加数据/加特征，优先做 |
| 钓鱼窃取密码（phishing） | 18 | 次大桶 → 也值得先做 |
| 异常邮件路由 | 7 | 占比小 → 可推迟 |
| 嵌在图片里的垃圾信息 | 5 | 占比小 → 可推迟 |
| 故意拼写变体（w4tches、med1cine） | 3 | 最小桶 → 放最后 |

```
验证集 500 封，错分 100 封：
  pharma   占错例 21 ─► 全修掉 ─► 错例最多从 100 降到 79（这桶天花板最大，优先投）
  phishing 占错例 18 ─► 全修掉 ─► 最多再消 18 个
  拼写变体 占错例 3  ─► 全修掉 ─► 收益上限 3 个（放心推迟）
```

### 天花板思想

**某类错误在错例中的占比 = 彻底修掉它之后指标提升的上限。**

- **天花板是上限不是承诺：实际收益通常达不到**，但占比小的桶可以放心推迟。
- 错误分析成本极低：人工看上百封邮件往往几个小时就够，却可能省下几个月投错方向的功夫。

（对应我们的 benchmark：与其笼统写一句"跨域掉点严重"，不如另划一个不参与排名的跨域错误分析子集（或先在验证集上做），抽约 100 个 best.pt 错例可视化，按"小目标漏检 / 遮挡漏检 / 背景误检"分桶——占比最大的桶，就是下一个循环该做的事；4 个测试集只用来出最终数字。）

一句话：**错误类型的占比就是修复收益的天花板——占错例 3% 的拼写变体，修得再完美也只值这 3%。**

### 追加：占比是上限，不是排序的全部——"占比 × 可修复性"二维判断

天花板逻辑只给了一半排序依据：占比 21% 意味着"修到完美**最多**赚 21%"，但"最多"≠"能拿到"。完整的优先级判断是：

```
优先级 ≈ 占比 ×（这个桶能被修掉的概率）÷（修掉它的代价）
```

几种"占比高但未必先做"的典型情况：

| 情况 | 例子 | 为什么不能只看占比 |
|---|---|---|
| 大桶修不动 | "图片模糊"占 30%，但数据源本来就是低分辨率 | 天花板高、地板也高，接近不可约误差，投入打水漂 |
| 小桶一行代码修掉 | "故意拼写变体"只占 3%，但一个 fuzzy-matching 特征全解决 | 收益/成本比可能反而最高 |
| 大桶已贴近人类水平 | 大猫 vs 猫本来就像，人也分不清 | 天花板要减去"人类也会错"的部分，剩下的才是可赚空间 |
| 一个改动同时修多桶 | 输入分辨率翻倍，小目标漏检和模糊误检一起降 | 杠杆型改动哪怕单桶占比不是最高也值得先做 |

课程的两步判断也是这个次序：先问**占比**（值不值得投入——占 5% 就别花几个月），再问**能不能修、要花多少**。垃圾邮件例子里 pharma 是最大桶所以优先，但前提是"有把握解决、成本可接受"。

（对应我们的 benchmark：假设"小目标漏检"占 40%、"标注框不一致"占 10%——前者要试更大输入分辨率，工程量大；后者可能只需统一标注协议后清洗数据，半天搞定。分桶先看占比定方向，动手前用性价比排顺序。）

一句话：**占比决定这桶"值不值得看"，可修复性决定它"值不值得先做"——分桶定方向，性价比定顺序。**

## 增加数据（P81）

错误分析找出了最值得投的桶，最常见的投入方向往往就是数据——先看两种相反的做法。

### 起小项目，还是先囤数据？
| 思路 | 做法 | 问题 |
|------|------|------|
| 先囤数据 | 先花几个月收集海量数据，再开始训练 | 周期长，且数据可能根本不是瓶颈 |
| 起小快跑（现代做法） | 小规模先跑通 → 错误分析定位瓶颈 → **针对性**扩充数据 | 基本没有 |

对应 P79 的迭代循环：训练 → 错误分析 → 再决定把钱花在加数据、加特征还是换模型上。

一句话：**加数据不在于多，在于"对症"——先跑通，再让错误分析告诉你该加什么。**

### 数据增强（Data Augmentation）
对已有数据施加随机变形，相当于"免费"扩充训练集：

| 数据类型 | 常用手段 |
|----------|----------|
| 图像 | 旋转、随机裁剪、翻转、形变（仿射/弹性）、颜色/对比度/亮度扰动 |
| 音频 | 叠加背景噪声、调整音量/音调 |

**合成数据（Synthetic Data）与数据增强并列**：不改造已有样本，而是凭空生成全新样本（GAN 生成、仿真渲染，如自动驾驶合成街景）。

### 原则：增强要模拟测试时真实出现的变形
> 做增强前先问一句：这种变形在测试/部署场景里真的会出现吗？

例如猫狗分类里小幅旋转合理，把猫倒转 180° 则只会引入不存在的分布。增强的本质是让训练分布贴近部署分布——若某个跨域测试集以夜间、雾天或俯拍为主，就针对性地加对应扰动（对应我们 4 个跨域测试集各自的偏移方向）。

一句话：**增强的目标不是"变多"，而是"变得像测试集"。**

### 该加真实数据吗？看学习曲线
结论同《模型诊断基础.md》：

```
高偏差：训练/验证误差都高且接近 -> 加数据基本没用，先扩模型/加特征
高方差：验证误差远高于训练误差  -> 加数据大概率有用
```

一句话：**学习曲线回答"该加数据还是该换模型"；增强近乎零成本，高方差/数据不足时值得先试——但它本质仍是加数据，救不了高偏差。**

## 迁移学习（P82）

### 三步流程
```
Step 1  在大数据集 A 上预训练（Pre-training），学通用特征
             |
Step 2  换掉输出层，匹配自己任务的类别数
             |
Step 3  在自己的数据集 B 上微调（Fine-tuning）
```

| 自己的数据量 | 微调策略 |
|--------------|----------|
| 很小 | 冻结预训练权重，只训练新的输出层 |
| 充足 | 输出层连同全网络一起微调（通常用较小学习率） |

### 何时有效
| 条件 | 说明 |
|------|------|
| 输入类型相似 | 预训练与下游任务都是图像（或都是文本、音频） |
| 数据量悬殊 | 预训练数据量远大于自己的数据 |
| 特征通用 | 低层特征（边缘、纹理、形状）跨任务可复用 |

### 典型例子
- 视觉：ImageNet 分类预训练 → 下游目标检测、语义分割
- NLP：BERT / GPT 在大规模语料上预训练 → 微调做情感分析、问答等

（对应我们：平时 train 时加载 COCO 预训练权重再在牛只数据上微调——YOLO 直接指定 `yolov8*.pt`，MMDetection 用 `load_from` 指向 COCO 检测预训练 checkpoint（2.x 的 `pretrained` 只初始化 backbone，3.x 已移除、改用 `model.backbone.init_cfg`）——就是 5 模型 benchmark 的默认起手式；跨域测试集掉点严重时，值得先试的通常是更充分的微调，而不是从头训练。）

一句话：**预训练学的是"怎么看清一张图"，微调学的是"认出图里是什么"。**

## 机器学习项目的完整周期（P83）

前面几集都在讲"怎么把单个模型调好"（P79–P82），这一集把镜头拉远：一个真实的机器学习项目从头到尾长什么样。

```
确定项目范围（要解决什么问题，X / y 大致是什么）
      |
      v
定义数据集（定义 y + 统一标注标准）
      |
      v
训练模型 + 迭代改进（P79 的循环）
      |
      v
部署（App / 服务器 / 嵌入式）
      |
      v
监控与维护 --性能衰减、重新收集数据--> 回到开头，形成闭环
```

### 阶段拆解

| 阶段 | 关键动作 |
|------|----------|
| 确定范围 | 明确要解决什么问题，X 和 y 大致是什么 |
| 定义数据集 | **定义 y、统一标注标准**——这一步常被低估 |
| 训练与迭代 | 进入 P79 循环：训练 -> 诊断 -> 加数据还是换模型 |
| 部署（deployment） | 选部署形态，接进业务 |
| 监控与维护（monitoring and maintenance） | 跟踪线上性能，发现衰减就回到开头 |

定义数据集时，"什么算正样本"必须前后一致：标注标准不统一，等于给模型喂互相矛盾的监督信号。（对应我们：开标前先写清"框整牛还是牛头""重度遮挡的牛标不标"，比事后返工便宜得多。）

### 部署的三种典型形态

| 形态 | 模型跑在哪 | 例子 |
|------|-----------|------|
| App / 软件 | 打包进应用，本地推理 | 手机拍照识别 |
| 服务器 | 部署在云端，业务经 API 调用 | 网页后台服务 |
| 嵌入式 / 边缘 | 烧录进低功耗硬件 | 传感器、摄像头模组 |

服务器形态的典型架构是客户端（App / 网页）经 API 调用推理服务器（inference server）——注意课程里 App 的角色是"调服务器的客户端"，与上表"App=本地推理"不是一回事。把这套系统做稳，属于 **MLOps**（系统地构建、部署、维护 ML 系统的实践）的活：预测要可靠高效、可扩展（scaling），还要记录日志、系统监控、模型更新流程。

### 部署之后：性能会衰减（data drift）

模型上线不是终点。**数据漂移（data drift）**指部署后输入 x 的分布变了，而模型还停留在训练时的分布上。常见诱因例如：采集设备老化、季节与光照变化、新设备上线。

> 与之相对的另一类是**概念漂移（concept drift）**：x→y 的映射本身变了。课程监控一节举的例子（语音系统里不断出现新的人名，触发重新收集数据重训）属于输入分布变化这一类。

（对应我们：牛只数据集来自不同牧场、不同设备、不同季节，4 个跨域测试集本质上就是预置好的 data drift——跨数据集 mAP 掉多少，测的正是模型对输入分布变化的鲁棒性。）

一句话：**部署不是终点，监控发现的数据漂移就是下一轮"重新收集数据、重新训练"的起点。**

## 公平性、偏见与伦理（P84）

机器学习系统越来越多地替人做决定，公平性（fairness）、偏见（bias）与伦理（ethics）因此不是可选项。

- 训练数据来自历史，历史里的偏见会被模型学走并放大。经典场景例如贷款审批、简历筛选：拿"过去谁被批准（贷款）/过去谁被录用（简历）"当标签，等于把过去的歧视当成监督信号；课程还举了人脸识别（深色肤色者更易被误判）和从历史招聘决定中学到肤色歧视的雇佣软件。
- 除偏见外还有"误用"类风险：深度伪造（deepfake）假消息、推荐算法加速假消息传播——技术本身中性，用法可以害人。
- 面向公众、会真实影响人的系统，不能只看总体准确率：要主动做**偏见审计（bias audit）**——分组检查错误率，评估系统可能对人造成的具体伤害。
- 建议：组建多元化团队（diverse team，成员在种族/性别/信仰等背景上多元，更容易发现盲区里的偏见），并设专人或固定流程把关，把公平性检查当成交付前的必过项，而不是靠个人自觉。

（对应我们：按数据来源分组看模型表现，本来就是跨域 benchmark 的日常操作。）

一句话：**偏见来自数据，伤害来自系统，把关要靠流程。**

## 倾斜数据集的错误指标（P85）

项目层面的内容到此为止，最后两集回到指标本身：先看让准确率失真的倾斜数据，再看阈值带来的 P/R 权衡。

当阳性/阴性比例极度悬殊时，称为倾斜数据集（Skewed dataset）。此时准确率（Accuracy）会严重失真。

**反例**：罕见病筛查，阳性率仅 0.5%。一个"无脑全预测阴性"的模型准确率高达 99.5%，却一个病人都抓不到——指标好看，模型毫无价值。

所以需要一套只盯"阳性抓得准不准、全不全"的指标。惯例是先把**罕见类设为阳性（y = 1）**，下面所有指标都围绕这个正类定义和报告。起点是混淆矩阵（Confusion matrix）：

| | 预测为阳性 | 预测为阴性 |
|---|---|---|
| **实际为阳性** | TP 真阳性 | FN 假阴性（漏报） |
| **实际为阴性** | FP 假阳性（误报） | TN 真阴性 |

由它导出两个核心指标：

| 指标 | 公式 | 回答的问题 | 俗称 |
|---|---|---|---|
| 精确率（Precision） | TP / (TP + FP) | 报出的阳性里，多少是真的？ | 查准 |
| 召回率（Recall） | TP / (TP + FN) | 真阳性里，被找出了多少？ | 查全 |

> 全预测阴性的模型 TP = 0：召回率 = 0/(0+FN) = 0；精确率 = 0/(0+0) = 0/0，数学上无定义（课程惯例记作 0）——总之 P、R 都拿不出手，而这正是准确率看不见的。

P、R 两个数不便直接比大小，常用 F1 分数（F1 score）汇总，即二者的调和平均（Harmonic mean）：

```
F1 = 2PR / (P + R)
```

为什么不用算术平均？数字例：P = 1.0、R = 0.02 时——

| 平均方式 | 结果 | 效果 |
|---|---|---|
| 算术平均 (P + R) / 2 | 0.51 | 表面"及格"，掩盖短板 |
| 调和平均 F1 | ≈ 0.04 | 狠罚短板，暴露问题 |

一句话：**调和平均被较差的一方主导，想 F1 高，P 和 R 谁都不能瘸。**

## 精确率与召回率的权衡（P86）

分类模型实际输出的是概率，需要判阳阈值（Threshold）才能落到"报/不报"的最终决定。默认锚点是 0.5——logistic 回归/神经网络输出 f ≥ 0.5 就判 1，下面的所有调整都从这个默认值出发：

```
预测概率 p ──► p ≥ 阈值 → 判阳性
           └► p <  阈值 → 判阴性

阈值 ↑（报得更保守）：精确率 ↑，召回率 ↓
阈值 ↓（报得更激进）：召回率 ↑，精确率 ↓
```

把阈值从 0 到 1 扫一遍，每个阈值得到一对 (R, P)，连成的轨迹就是 PR 曲线（Precision-Recall curve）——它画出这个模型在两种错误之间所有可达的折中。

阈值没有唯一正确答案，按业务代价选：

| 场景 | 主导代价 | 阈值取向 |
|---|---|---|
| 误报代价大（冤枉好人、人工复核成本高） | FP | 调高，保精确率 |
| 漏报代价大（罕见病漏诊、欺诈漏检） | FN | 调低，保召回率 |
| 两边代价相当 / 需要自动选择 | — | 在交叉验证集上扫一串阈值，取 F1 最高者 |

课程口径是最后一行：在**交叉验证集**上试扫一串阈值、各算 F1、取最高——老规矩再次生效，能反复看的只有验证集，测试集只留到最后，所以别拿测试集选阈值。

（对应我们：检测的 mAP 本质是先对每个类别算 PR 曲线下面积（AP）再在类别上求平均，P/R 权衡已内嵌在指标里，所以按 fitness 选 best.pt 时无需先定阈值；但部署时 YOLO 的置信度 conf 阈值才真正决定输出框的 P/R——牛只统计是"多报几头"还是"漏检几头"，就在这一格上拍板。）

一句话：**P/R 权衡不是模型缺陷，是业务决策——曲线由模型决定，阈值由代价决定。**
